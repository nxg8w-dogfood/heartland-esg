# Heartland ESG

A tool used to measure co2 emissions on a company

## Running it

Heartland ESG is being rebuilt as a [Power Apps code app](https://learn.microsoft.com/power-apps/developer/code-apps/overview):
React and TypeScript built with Vite, with Dataverse behind it. Why is in
[docs/adr/0001](docs/adr/0001-rebuild-as-power-apps-code-app.md).

### Prerequisites

- Node.js 24 (LTS) and npm
- Git

### Run it locally

```bash
npm ci
npm run dev
```

Vite prints a local URL. Until Dataverse is in place (ADR 0005), data is kept as a draft in your browser. This runs the UI on its own, outside Power Platform, which is
enough for UI work and for the calculation engine in `src/calc/`.

Plate lookups on the Bilpark page (under Scope 1) answer with example data in `npm run dev`, because the real
lookup goes through a connector that only exists inside Power Platform (ADR 0009). The page says
which plates it knows. Inside Power Apps, until the connector is set up
(`connectors/motorapi/README.md`), cars are entered by hand.

### Check your change

These are the same steps CI runs on every pull request:

```bash
npm run lint
npm test
npm run build
```

Use `npm run test:watch` to rerun tests while you work.

### Update the ESG owner's rules

Spend-based tagging uses the ESG owner's `kontoregler.csv` and `posteringsregler.csv` (ADR 0015).
They aren't committed; the app reads `src/data/scope3Rules.ts`, which is generated from them.
When the ESG owner sends new versions, regenerate it on a branch and review the diff:

```bash
node scripts/scope3-rules-seed.ts <path>/kontoregler.csv <path>/posteringsregler.csv
```

The script stops on a column or value it doesn't recognise, rather than guessing.

### Update the exchange rates

Spend lines are converted at the exchange rate on their date (ADR 0016), from a table of the
ECB's daily euro reference rates in `src/data/exchangeRates.ts`.

Every Monday the `exchange-rates` workflow regenerates the table, pushes any change to
`chore/exchange-rates` and runs CI on it. GitHub Actions isn't allowed to open pull requests in
this repository, so open it yourself: the run's summary has an *Open the pull request* link. If
one is already open, the workflow updates it. Review and merge it like any other change. Before
closing a reporting period, run it by hand: **Actions → exchange-rates → Run workflow**. To
update the table locally instead:

```bash
node scripts/exchange-rates.ts
```

A line dated after the table's last day uses the fixed rate in `src/data/currencies.ts` and says
so; a currency with no fixed rate (GBP, USD, NOK) is left pending until the table is updated.

### Run it inside Power Platform

This needs a Power Platform environment with code apps enabled. The
[Power Apps CLI](https://learn.microsoft.com/power-apps/developer/code-apps/reference/cli)
is a dev dependency, so `npx pa` runs the project's pinned version:

```bash
npx pa app init --display-name "Heartland ESG" --environment-id <environment-id>
npx pa app run
```

Open the URL labelled **Local Play** in the browser profile you use for the Power Platform
tenant. `pa app init` writes `power.config.json` for your own environment. It's git-ignored;
the shared environments' configs live in `deploy/`. `npm run dev` prints the same Local Play URL
once `power.config.json` exists.

Inside Power Apps the app stores everything in Dataverse, in the `hlesg_` tables (ADR 0005).
Opened directly at http://localhost:5173 it can't reach Dataverse, so it falls back to the
browser draft. The services in `src/generated/` (and `.power/`) are generated by
`npx pa app add data-source --connector dataverse --table <table>`; don't edit them by hand,
and regenerate them when a table changes.

Fetching consumption from Eloverblik and Varmeoverblik (Scope 2, ADR 0011) calls those APIs from
the browser. Inside Power Apps that's blocked until an environment admin adds
`https://api.eloverblik.dk` and `https://api.varmeoverblik.dk` to `connect-src` in the
environment's
[code-app Content Security Policy](https://learn.microsoft.com/power-apps/developer/code-apps/how-to/content-security-policy).
`npm run dev` in a plain browser needs no change.

### Deploy

Deploys run from `.github/workflows/deploy.yml`, never from a laptop:

- **dev** deploys on every push to `main`.
- **test** and **prod** deploy when started by hand: **Actions → deploy → Run workflow**.
  To send prod exactly what was checked on test, give that commit's SHA (see
  [docs/deploy.md](docs/deploy.md#promote-a-tested-commit-to-prod)).

Each environment needs a one-time setup first (a Power Platform environment, a service
principal and a GitHub environment). Until then its deploy run warns and deploys nothing.
The setup steps are in [docs/deploy.md](docs/deploy.md). The reasoning is in ADR 0003.

### Dataverse tables

The tables are defined in `src/dataverse/schema.ts` and created with a script (ADR 0007). It
creates missing tables and columns, and never changes or deletes existing ones. Sign in to the
environment's tenant with the Azure CLI, check what it would do with `--dry-run`, then apply:

```bash
az login --tenant <tenant-id>
npm run dataverse:apply -- --url https://<org>.crm4.dynamics.com --dry-run
npm run dataverse:apply -- --url https://<org>.crm4.dynamics.com
```

The same script creates the security roles and keeps their privileges in step with
`src/dataverse/roles.ts`. Each company in the group gets its own business unit and owner team
(ADR 0006):

```bash
npm run dataverse:company -- --url https://<org>.crm4.dynamics.com --name "Heartland A/S"
```

You need the System Administrator role in the environment.

### Layout

| Path | What it is |
| --- | --- |
| `src/calc/` | Emission calculations as plain TypeScript, with tests next to them. No UI, no Power Platform dependencies. |
| `src/data/factors.ts` | The emission factor table, copied value for value from the original app, plus the DK1/DK2 electricity factors (ADR 0012). `municipalities.ts` maps each municipality to its price area. |
| `src/scope1/`, `src/scope2/`, `src/scope3/`, `src/factors/` | The Scope 1, 2 and 3 screens, and the factor table. |
| `src/utility/` | Fetching monthly electricity (Eloverblik) and district-heating (Varmeoverblik) consumption, called from the Scope 2 screen (ADR 0011), and creating locations from fetched meters (ADR 0012). |
| `src/ledger/` | The Kontoplan screen: importing ledger postings (CSV or XLSX, see ADR 0004) and tagging them by rules, and the postings section the Scope 3 category pages show. |
| `src/data/scope3Rules.ts`, `src/data/spendFactorRegister.ts` | The ESG owner's account and posting rules, and the register mapping each FaktorID to a factor and EXIOBASE sector (ADR 0015). The rules file is generated; see *Update the ESG owner's rules*. |
| `src/calc/exchangeRates.ts`, `src/data/exchangeRates.ts` | Exchange rates on a line's date: the lookup, and the ECB's daily rates generated by `scripts/exchange-rates.ts` (ADR 0016). |
| `src/vehicles/` | The Bilpark screen, a page under Scope 1 (`#/scope1/bilpark`): the company's diesel and petrol cars, looked up by plate through MotorAPI (ADR 0009). The km-to-litres calculation is in `src/calc/vehicles.ts`. |
| `connectors/motorapi/` | The MotorAPI custom connector and the API Management policy that adds the key from Key Vault, with setup steps (ADR 0009). |
| `infra/motorapi/` | Bicep for the plate-lookup proxy: API Management, the Entra app registrations, Key Vault access and a budget (ADR 0009). |
| `src/group/` | The Koncern screen: the group's companies, ownership shares, each company's fiscal periods (ADR 0013) and summary (ADR 0006). The period picked in the header is what every page reports on. |
| `src/dataverse/`, `scripts/dataverse-*.ts` | The Dataverse tables and security roles as code, and the scripts that set them up in an environment (ADR 0007). |
| `src/storage/` | Saving and loading the group and each company's account (`GroupStore`): Dataverse inside Power Apps (`dataverse/`), and a browser draft locally. |
| `src/generated/`, `.power/` | Generated by the Power Apps CLI for the Dataverse tables. Don't edit. |
| `src/brand/` | The HEARTLAND Design System tokens (`tokens.css`) and logotype (ADR 0008). |
| `src/index.css` | The app's styles, built only on the `--hl-*` tokens. |
| `src/App.tsx`, `src/pages.ts` | The app shell, and the pages it links to. Scope 3 has its own pages under `#/scope3/` (overview, one per calculated category, settings last), listed in `src/scope3/subpages.ts`. Scope 1 has two, the emission lines and Bilpark, listed in `src/scope1/subpages.ts`; the old `#/bilpark` address is redirected there (`movedHash` in `src/pages.ts`). |
| `docs/adr/` | Architecture decisions. |
| `deploy/<env>/power.config.json` | Per-environment app config used by the deploy workflow. |
| `.github/workflows/ci.yml` | Lint, test, build and dependency audit, plus a gitleaks scan of the full history. |
| `.github/workflows/deploy.yml` | Publishes the app to dev, test or prod. |
| `.github/workflows/exchange-rates.yml` | Weekly: regenerates the exchange-rate table onto `chore/exchange-rates` and runs CI on it, ready for a pull request (ADR 0016). |

## Working here

This repository was started through aiG8way. The agreed brief is in `CLAUDE.md` / `AGENTS.md`;
the security controls that apply are in `SECURITY.md`.

Guardrails this project carries:

- **README with run instructions** — Every repository opens with a README that states what the project is, how to run it locally, and how to deploy it. A newcomer should be productive without asking anyone.
- **Automated tests run on every pull request** — A test suite exists and CI blocks a merge when it fails. Coverage targets are per-project; the non-negotiable part is that the suite runs unattended.
- **Protected default branch** — No direct pushes to the default branch. Changes land through a pull request with at least one review.
- **CI builds the project from a clean checkout** — The pipeline installs, lints, tests and builds from scratch. "Works on my machine" is not a build.
- **Deployment is automated per environment** — Deploys are triggered from the pipeline, not from a laptop, and each environment has its own configuration.
- **No secrets in source control** — Secrets live in Key Vault or environment configuration. The repository is scanned for committed credentials and the scan blocks the merge.
- **Dependency and vulnerability scanning** — Dependencies are scanned on a schedule, and known-vulnerable versions are patched inside the agreed window.
- **Authorisation checked server-side** — Permissions are enforced in the backend. Hiding a button in the UI is presentation, never protection.
- **License and ownership declared** — The repository states its licence and the owning team, so it is clear who maintains it and on what terms it may be reused.
- **Architecture decisions recorded** — Significant technical decisions are written down as short ADRs in docs/adr/, including the options rejected and why.
